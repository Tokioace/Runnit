# Hosted synthetic Auth and REST smoke

Manual only, on develop. Never configure production credentials. Use an independently approved disposable Supabase project containing only synthetic data, with the candidate schema and session guard installed. No project is provisioned by this change. In the GitHub environment runnit-synthetic-api-test configure RUNNIT_NATIVE_TEST_REF, RUNNIT_NATIVE_TEST_DATA_CONFIRMED=synthetic-only (variables), and the publishable key plus RUNNIT_API_TEST_EMAIL_A/B, RUNNIT_API_TEST_PASSWORD_A/B, RUNNIT_API_TEST_ID_A/B (secrets). Create two confirmed email/password accounts with runnit-test- prefixed addresses and distinct exact Auth UUIDs. Ensure both have their own runner_stats_preferences row. Never copy real users or use an administrator key.

Dispatch Hosted synthetic Auth API smoke on develop with confirm_synthetic=true. The script signs into A twice and B once, checks exact identities and own preference rows, denies cross-account and anonymous preference reads, logs out one A session locally, retries its original bearer against protected REST rows, and verifies the second A session and B remain active. Logout cleanup targets only sessions created by this run. No app row writes, signup, admin key, data export, or secret logging. It creates/revokes real test sessions when explicitly run. The script uses bounded HTTPS requests without redirects and rejects the known production ref. Synthetic confirmation and exact accounts do not prove that an arbitrary other project contains only synthetic data; operator review is mandatory. Failed network/server responses are not accepted as privacy denial. Real Auth/API verification remains pending until a configured test project runs this workflow. Unit tests mock transport and verify failures, not real GoTrue behavior. OTP email, OAuth, refresh, Realtime, GraphQL, native Keychain and physical sensors are separate gates.

References: https://supabase.com/docs/guides/auth/sessions and https://supabase.com/docs/guides/auth/signout .

## Refresh rotation follow-up
PR #256 passed the mocked transport tests. The hosted smoke now also decodes the returned JWT session_id/sub for test correlation only (not authorization), verifies three distinct sessions, rotates the first A refresh token and checks stable session ID with changed refresh token, then logs out that session and verifies both access token generations fail protected reads. It retries the last refresh credential after logout and requires an explicit Auth rejection code; an erroneously accepted refresh fails the test and is tracked for cleanup. The second A session must retain its private row access and refresh successfully. Deliberately does not replay rotated tokens while a session is active because Supabase documents a default ten-second reuse window and a parent-token recovery exception. Network failures, rate limits, arbitrary 400s and 5xx are not accepted as revocation. See https://supabase.com/docs/guides/auth/sessions . The updated automated tests still mock the transport. Real hosted execution needs configured synthetic accounts and the staged schema; not dispatched by this change. No change to actual application auth or production data.

## Profile column privacy — release gate R03
Both synthetic public profiles must have a non-null nickname and distinct known IDs. In addition to the private preference checks, the smoke verifies each authenticated account can retrieve the other's id and username, with no extra fields. Each account then attempts explicit reads of location, city, country, joined_at and wildcard on its own and the other synthetic profile. Every restricted request must return HTTP 403 with PostgreSQL insufficient privilege code 42501. Successful empty results, unrelated errors and missing columns do not prove column-level privilege denial. Anonymous profile ID visibility is also checked. Only synthetic fixtures may be used; no response body, nickname or coordinates are logged, and no app data is written. See the checked-in privacy migration and https://supabase.com/docs/guides/database/postgres/column-level-security. Mocked transport tests are not hosted API evidence. The approved synthetic environment and actual smoke run remain outstanding. No production policy, schema or deployment changes.

## Revocation evidence before JWT expiry
Before local logout, both the original and refreshed A access tokens must successfully read the protected own preference and profile rows. Their JWT `exp` claims must leave at least 30 seconds of validity at the beginning and end of the positive and negative checks, using the runner clock. A missing/invalid expiry, already rejected token, or token expiring during the proof fails the smoke instead of counting as successful revocation. The operator must keep the clock synchronized and use a test JWT lifetime long enough for the checks. Supabase access JWTs can remain valid after logout until expiry: https://supabase.com/docs/guides/auth/signout . This is a hosted-test evidence safeguard, not a new runtime authorization rule.
