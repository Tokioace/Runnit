# iOS preview — stage 1

Decision: Capacitor 8.6.2, SPM, bundled Vite assets, no remote web URL. This preserves the React UI and keeps the existing web build/dependencies unchanged. Capacitor 8 requires Node 22+ and Xcode 26+, also consistent with Apple's current minimum upload SDK (https://capacitorjs.com/docs/getting-started/environment-setup and https://developer.apple.com/news/upcoming-requirements/?id=04282026a). Provisional bundle identifier com.tokioace.runnit.preview; not registered or confirmed for production. Do not distribute under this identifier.

The PR workflow on Linux creates a separate shell input artifact with the web build, pinned direct dependencies and resolved npm lockfile, runs npm audit and the Capacitor CLI. It intentionally uses a nonfunctional placeholder backend; no secrets or live data. The generated transitive lockfile must be reviewed and committed into the native shell before treating future builds as reproducible; first resolution may vary. The existing root lock stays untouched. The optional manual macOS job uses the lockfile from the same run and builds an unsigned simulator App.app. It is not a device IPA, TestFlight upload, or approved native app. The script adds purpose strings only for existing location and motion use. No background-location or microphone permission.

The macOS job requires user-approved runner minutes (potential billing); do not automatically dispatch it on every PR. Run via Actions > iOS preview preparation > Run workflow on develop with build_simulator=true, after approval. No Apple credentials are required for unsigned simulator compile. Signing, distribution and real devices require Apple developer enrollment, a registered bundle ID, certificate/provisioning, App Store Connect and test backend. No macOS/Xcode or public npm registry access in the current local execution environment. PR check results and optional simulator compile are the actual evidence.

## Native session vault — stage 3
The iOS WebView now selects a custom Supabase storage adapter. It uses the native Capacitor bridge (nativePromise, version-pinned native runtime) and a small Swift plugin registered by a subclass of CAPBridgeViewController. The installer modifies only the freshly generated SceneDelegate following Capacitor 8.5+ lifecycle guidance (https://capacitorjs.com/docs/updating/8-5 and https://capacitorjs.com/docs/ios/custom-code); unknown templates stop compilation. Keychain entries are device-only, available while unlocked, non-synchronizing, app-service-scoped; a non-backed-up installation marker clears surviving app-vault entries on first use after reinstall. No extra npm dependencies. Native bridge logging is disabled. Existing WebView legacy auth keys are removed best-effort without importing them; Safari uses the original SDK storage unchanged. Missing bridge gives volatile storage only; a present bridge error propagates, not a disk fallback. No custom SDK storage key. This protects at-rest data, not a compromised executing WebView; JWTs still enter JS memory as required by the SDK. Actual Xcode compilation, plugin registration, Keychain read/write/refresh/sign-out, lock/unlock, reinstall, multiple scenes, bridge error and old token cleanup tests are required on real devices before release. No actual native build, production Auth change, or paid runner was invoked here.

## Native sensor probe — stage 4
App-local foreground diagnostic using Core Location and CMMotionManager device motion. Start only after an explicit tap and authorized location; first tap may request permission and requires another tap. Core Motion requests 50 Hz (actual rate displayed, not guaranteed). Native counts accepted/rejected fresh GPS fixes, last horizontal accuracy, motion samples and intervals >250 ms; no coordinates or raw motion data cross the JS bridge. Native hard limit 30 s, stops on resign-active, sensor failure or explicit stop; JS also stops on page hide/unmount and scopes reads/stops to the native run ID. The separate /native-sensors route is reachable from GPS field test only in bundled iOS. No database upload, no stored result, no ranking and no changes to existing race/Ghost Run or browser measurement. Compare field observations with existing web diagnostics before selecting a production sensor pipeline. A count of received samples is not evidence of accurate sprint distance, step count or timing. Xcode compile, real permission behavior, lifecycle/scene handling, measured sampling, lock/unlock and repeated tests are outstanding. No macOS job or paid service was triggered.
## Native sprint reference test — stage 5
Within the 30 s native foreground probe, a runner may explicitly arm one 50/75/100 m experiment during the first 15 s with a fresh (<=3 s), <=15 m accuracy start fix. The native pure Swift estimator uses straight-line displacement, rejects impossible segment speed (>12 m/s), poor accuracy, duplicate/too-fast samples, invalid values and invalidates gaps >3 s or a detected wall-clock shift. Two accepted fixes beyond the target are required; interpolate the first crossing. It cannot detect a precise motion start, lane geometry or a false but plausible GPS track. Native coordinates remain in transient memory and are cleared on probe end; only aggregate diagnostic values enter JS. No server data, ranking or production race change. Reference entry is optional and comparable only for the same manual start and independently marked finish. Displayed precision is not accuracy. Linux Swift synthetic tests compile the pure estimator (not the iOS bridge); JS tests check aggregate/command validation. Actual native compilation and outdoor paired trials still required. Do not increase release confidence from synthetic tests alone.

## Native motion candidates — stage 6
The same pure Swift file now includes a bounded 3000-sample in-memory motion estimator. Core Motion userAcceleration is converted from g to m/s². Peak threshold, prominence, 190 ms minimum spacing and rhythm windows follow the experimental web sprint cadence approach, not the 450 ms walking counter. Summary is clipped to the manually armed sprint start and interpolated GPS crossing (or the probe window if not armed); no peaks after finish or before start are counted. At least 70% coverage, no gaps over 250 ms, and six peaks with consistent intervals are required for cadence. Reports distinguish incomplete/insufficient/irregular/sprint-like/other-rhythm. Raw samples are cleared on finish and only aggregate results cross the bridge. Manual step comparison is local, optional and only shown for completed measurement windows or manually stopped plain probes. No raw samples, uploads, production races, or leaderboard changes. A shaken device can produce a regular rhythm; this is not proof of real steps or anti-cheat. Pure Swift synthetic tests cover 200/100 spm, stationary data, invalid samples, gaps and clipped windows; bridge tests check validation. Still requires Xcode and physical pocket/hand/vehicle tests and reference counts. No release percentage increase based solely on more unvalidated native code.

## Native sensor consistency — stage 7
The experimental screen evaluates only a completed GPS sprint and the motion summary of the same start-to-interpolated-finish window. Missing/poor coverage, interruptions, slow movement or irregular rhythm remain insufficient. Provisional generous bounds (average GPS speed 3–12 m/s, distance per candidate 0.3–3 m when >=6 candidates, whole-window candidate rate 100–320/min, recent rhythm 140–300/min, relative cadence deviation 40%) flag discrepancies; zero detected peaks despite sufficient coverage is a diagnostic flag, not cheating. A compatible result is also explicitly unverified. These are heuristic ranges chosen for initial field trials, not calibrated physiological limits. They may misclassify genuine runners and miss manipulation. No changes to competition, backend, storage or public rankings. No new raw data. Real device trials must include stationary, walking, pocket sprint, hand sprint, missing signals, and controlled non-running motion (no unsafe road tests). Use measured course and independent synchronized start/finish and step count. Log false warnings and misses before considering any enforcement. The native build and real field trials remain release gates.

## Native account recovery using existing email OTP
The existing native sign-in screen now explicitly offers forgotten-password recovery using the email code for an existing account. After verified OTP login, the runner can open Profil → Konto → Passwort ändern. The existing account mutation guard and Auth identity check still protect the password update; no recovery token or password is read from a URL, no custom deep link and no new account is created by the native OTP request. This is not a dedicated password-reset token flow. The Magic Link email template must include the six-digit `{{ .Token }}`, and SMTP delivery and the actual Auth password-update/reauthentication policy must work. Before release, verify with a synthetic existing account: forgotten-password code request, wrong/expired code rejected, successful code login to the original UUID, password change in account settings, logout, login with the new password, old-password rejection, and account/session isolation. Restore the synthetic fixture's password securely after testing. Do not record email codes, password values, or real identity details. No backend settings changed, and no real email was sent or password changed in this PR.

## App-local required-reason privacy manifest
The native foreground probe uses ProcessInfo.processInfo.systemUptime to measure elapsed intervals, enforce its 30-second deadline and correlate motion timestamps; raw boot time stays on device. Apple's current required-reason list includes systemUptime under NSPrivacyAccessedAPICategorySystemBootTime and reason 35F9.1 for elapsed time/timers (https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype). The checked-in preview PrivacyInfo.xcprivacy declares that specific use, not an assertion that the app collects no data or performs no tracking. Preparation inserts the resource into the pinned Capacitor 8.6.2 SPM Xcode template (reviewed upstream project.pbxproj), hashes both source and installed copies, and validates the exact declaration in the compiled App.app. This is a partial preview manifest only: inspect final signed binary, framework/SDK manifests, other required-reason APIs, tracking and actual data collection before finalizing the production manifest and App Store privacy answers. No claim of App Store compliance, no native compile or submission, and no runtime sensor changes.
