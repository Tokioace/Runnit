# Account deletion — release gate

This PR implements the in-app request and private, idempotent request storage. **Not active:** the SQL is a release candidate and the UI is gated by VITE_ACCOUNT_DELETION_REQUESTS_ENABLED=true. Do not set the flag until deployment and end-to-end fulfillment, reasonable processing timeframe and completion email have been tested. Apple permits manual fulfillment but requires in-app initiation, actual account/data removal, user information about processing time and completion confirmation (https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion/). Do not advertise compliance yet.

Read-only catalog review: public.users has no FK to auth.users; removing Auth alone leaves public profile and app data. ghost_runs/ghost_run_sessions/duel_results reference public.users with cascade; hosted duels cascade and opponent duels set challenger null (existing cancellation trigger may prevent FK updates on cancelled records); runner_stats_preferences references auth.users with cascade. Auth sessions/identities cascade. Existing duel results can include the other runner's data. A production deletion policy and test must decide how to preserve opponents' legitimate history while removing the deleted player's personal data. Do not simply run bulk deletes. Inspect Storage ownership, provider token revocation (especially Apple), logs/backups/retention and any additional data processors.

Operator checklist before enabling: provide privacy notice, controller contact, realistic processing target and confirmation email; verify identity and request from queue; design transactional application-data cleanup, test all relationships in a separate environment with synthetic accounts, verify session revocation and stale JWT access, delete Auth via server-only admin API, verify data removal and notify requester. Keep only lawfully necessary records. No actual accounts deleted, no production data modified, no secrets added. The CI fixture checks real role isolation, duplicate rejection, server-owned timestamp, and FK cascade of the request record, not full account erasure.

## Erasure guard candidate (follow-up)
Read-only catalog inspection confirmed zero orphan public profiles and zero Storage buckets at inspection time. The proposed FK binds profiles to auth identities and prevents stale JWTs from recreating an erased profile. It also enables cascading erasure of existing owner-linked app data when the trusted admin deletes an Auth account. Direct authenticated profile DELETE is revoked (the existing table grant was present, even though RLS also applies). The private trigger locks associated duels and rejects deletion if another participant or another runner's result exists. This is an explicit **temporary fail-closed release blocker**, not a permanent refusal to honor an erasure request. A shared-duel anonymization or archival policy is required before activation. The synthetic PostgreSQL fixture checks both sides of a shared match, rollback, owner-only deletion, stale-token profile recreation and unrelated result preservation. No existing data was removed. Never activate the UI or candidate before shared-race handling, real Auth admin API tests, stale-token access across all endpoints, privacy notice, provider revocation and completion email are implemented and verified. Do not use direct SQL to delete real Auth accounts; use the trusted server admin API once the final migration and workflow are approved.

## Shared race erasure follow-up
The new candidate supersedes the fail-closed guard for terminal shared races only. Proposed policy: preserve surviving runner's own result privately, without original race ID, rival ID/name/time, location or win/loss; remove the original shared record and public ranking contribution. Active/unknown status or malformed historical results still block the deletion, requiring operator resolution. Archive is owner-readable and server-written only, cascades on later owner deletion; no public ranking uses it. The existing stats history displays archived own times as private, non-scoring entries when the deletion feature flag is enabled. This intentionally does not preserve public wins or personal competitive best-time totals for erased shared races. No assertion of legal anonymization: timing may still be correlatable with external records, and data minimization/legal basis must be reviewed. No production changes. Synthetic host/challenger deletion, rollback, active match rejection, owner isolation, ranking removal and later archive deletion are covered; real Auth API/notification workflow, stale JWT audit and privacy notice remain release blockers.

## Operator rehearsal — test only
The server-only script scripts/account-erasure-test.mjs has a dry run and an explicitly confirmed synthetic deletion mode. It refuses the known production project, custom/mismatched URL, unconfirmed email identities, external providers, missing request, active matched races, unknown counts and missing schema gate. It uses existing Supabase SDK and a secret supplied through environment variables on a trusted operator machine. Never set a VITE_ variable for the key, never use CI secrets or put credentials in logs. The test gate SQL is installed only in an approved disposable project after prior candidates. The gate checks structural prerequisites, not every trigger behavior; actual integration testing remains necessary. After Auth admin hard deletion, verify a 404 and zero owner-related records, including original shared duels and personal archive. A network failure after deletion may require manual reconciliation, not blind retries. The script does not send mail or store recipient data; completion notification is deliberately an outstanding operator task. An actual disposable project, synthetic user, mail process, stale JWT audit, provider revocation and final privacy/retention decisions remain necessary. No live user deletion or production deployment was performed. Mock tests exercise all control paths without network or credentials.

## Revoked session access candidate
The live catalog identified six authenticated-only SECURITY DEFINER RPCs. The staged SQL adds a private, fixed-search-path session helper which checks signed JWT session_id against auth.sessions (identity and not_after); restrictive policies protect all eight application tables including the two proposed privacy tables, without replacing existing ownership checks. The six existing privileged RPCs are explicitly guarded, retaining their signatures and existing permissions; submit uses the staged result guard. Public opt-in Beta ranking RPCs intentionally remain public. The helper returns false for missing/malformed claims or revoked/mismatched sessions. Synthetic PostgreSQL tests validate live session, malformed/foreign/expired session, removed session, read and write denial, and public ranking visibility. This does not revoke a signed JWT cryptographically or stop an already executing request; actual Auth sign-out, deletion, PostgREST, GraphQL, Realtime subscription/cache behavior, OAuth and field tests are still needed. No live database or auth configuration changed. Verify current production RPC definitions against this snapshot before generating a migration.
